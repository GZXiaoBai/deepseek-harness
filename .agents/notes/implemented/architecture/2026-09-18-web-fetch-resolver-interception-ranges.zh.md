# Agent Note: web fetch 接受已声明的解析器拦截范围

Status: implemented

[English](2026-09-18-web-fetch-resolver-interception-ranges.md) | 中文

## 问题

`web-fetch-http` 会拒绝 `ipaddr.js` 未归类为全局可达单播的每一个解析结果，因为 URL 由模型选择，指向私有、回环或链路本地地址的目的地会暴露本机服务。而某些部署的解析器会拦截域名解析——例如 VPN 客户端运行 TUN 并使用 fake-IP 池——对每次查询都返回该池内的地址。此时目的地从来不是提供方校验的那个地址：隧道把占位地址转发给代理，由代理在远端解析真实源站。`dig example.com` 返回 `198.18.0.12`，于是所有抓取都以 `WEB_BLOCKED_URL` 失败，而同一 URL 用 `curl` 却能成功；这项检查拒绝了可用的网络配置，却没有保护任何模型能够触及的东西。

## 决策

`web-fetch-http` 增加受校验的配置字段 `resolverInterceptionRanges`（默认 `[]`）。落在已声明范围内的解析结果会被接受为目的地；连接仍然固定到已校验的地址集合，地址策略其余部分不变。条目必须是完全落在 `198.18.0.0/15`（RFC 2544 benchmarking）或 `240.0.0.0/4`（reserved）之内的 IPv4 CIDR：这两个池在公网上不可路由、也永远不会指向本机服务，因此声明无法打开回环、私有、链路本地、运营商级 NAT 或 ULA 空间。格式错误、非 IPv4 或超出池范围的条目会在插件构造时直接失败。IP 字面量永远不会被视为拦截结果，因为字面量本身就是目的地，不存在解析过程。部署在 profile patch 中声明自己的池：

```yaml
- id: web-fetch-http
  config:
    resolverInterceptionRanges: ['198.18.0.0/15']
```

## 考虑过的替代方案

**无条件接受 benchmarking 范围。** 这为了照顾一种组网方式而放宽所有部署的安全策略，而且无法覆盖客户端选用其他池的部署。

**自动检测拦截。** 没有任何可观测事实能区分 fake-IP 池与真正错误或恶意的解析结果；靠推断意图会让拒绝行为变得不可预测。

**改用代理配置，让抓取跳过地址校验。** 这条路径已经存在，但该部署的客户端没有暴露本地代理端口，而且那会把 DNS 策略移出 harness。

## 结果

经由被拦截解析器的抓取现在会按部署自身的路由到达源站，这正是运维方的意图。声明按部署生效而非全局生效，未声明范围的部署与此前完全一致。验证覆盖构造期校验、仅在已声明范围内接受、字面量豁免以及解析器接线。
